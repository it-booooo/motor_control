# AK10-9 V3.0 馬達特性化測試台

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
[![Python 3.10+](https://img.shields.io/badge/python-3.10+-blue.svg)](https://www.python.org/)

一套低成本的準直驅（QDD）致動器特性化工具，針對 **CubeMars AK10-9 V3.0 KV60**。

用途：在機構設計凍結之前，先把馬達的真實能力量出來，
產出「實測 Kt、飽和點、反驅阻力、熱時間常數」四組參數，
當作後續並聯踝關節（SPU / RSU）幾何最佳化的輸入。

**特色**

- 依 CubeMars AK 系列 V3.0 手冊實作的 MIT 力控模式 CAN 協議（Python）
- CAN 與 load cell 兩路資料同步擷取，含資料新鮮度（age）記錄
- 五組實驗腳本：縮放常數驗證、Kt 校正、正反向不對稱、反驅阻力、熱衰減
- 分析端自動分離線性區與飽和區、以指數擬合外推熱時間常數
- **附內建模擬器：沒有硬體也能把整條分析流程跑通**
- **PySide6 桌面 GUI：硬體設定、五組實驗、即時遙測、停止保護、模擬與分析整合在同一視窗**

## 桌面 GUI

GUI 參考 `2026-NCB-summer-intern` 的分層方式。根目錄 `__main__.py` 是唯一的應用程式
入口，負責建立 `QApplication`、套用樣式及顯示主視窗；`src/main_window.py` 只保留
`MainWindow` 應用程式外殼。Composer 建立各功能面板，Controller 負責流程協調，耗時
的硬體量測與資料分析則交由背景 Worker 執行。長時間熱實驗不會凍結介面，關閉視窗或
按下紅色停止按鈕時會先把馬達切回 idle，再安全關閉 CSV。

安裝後由唯一入口啟動：

```bash
pip install -r requirements.txt
python __main__.py
```

GUI 包含：

- 「硬體與安全」：CAN 介面／通道、bitrate、Motor ID、load cell 序列埠、力臂長度、
  記錄頻率、資料目錄及扭力／電流／溫度安全上限。設定只套用到當次執行，不會偷偷改寫
  `config.py`。
- 「實驗設定」：縮放驗證、Kt、正反向、反驅及熱衰減的所有原始參數；縮放驗證會用
  對話框引導 90° 手動轉軸與拆除力臂兩個步驟。
- 「即時遙測」：位置、轉速、電流、溫度、load cell 力、指令與實測扭力；若已安裝
  `pyqtgraph`，同時顯示即時曲線。
- 「資料分析與模擬」：可產生四組 README 所述的假資料，也可選擇任一量測 CSV，執行
  原有 `analyze.py` 並直接預覽輸出圖。量測完成後預設會自動分析。

建議第一次操作順序：

1. 在「硬體與安全」確認 Windows/Linux 對應的 CAN 與序列埠設定，先把安全扭力設為
   **3 N·m**，按「測試 CAN 與 Load cell」。
2. 依序勾選三項現場安全確認；這些勾選不會取代機械限位與實體 E-stop。
3. 先執行「0. 縮放常數驗證」，確認位置與速度換算，再依 README 順序執行其餘實驗。
4. 紅色「緊急停止 / Motor Idle」會立即清除扭力指令，並保留停止前已寫入的部分 CSV。

> GUI 的停止按鈕屬於軟體保護。USB、作業系統或程式本身失效時仍可能無法動作，
> 因此實體電源開關／E-stop 必須保持在伸手可及處。

### 建立單一 Windows 執行檔

與參考專案相同，根目錄的 `build.py` 會先檢查完整依賴與舊 EXE 是否被執行中的程序
鎖定，再以根目錄 `__main__.py` 為唯一入口，使用 PyInstaller 進行 clean
one-file/windowed 建置：

```bash
python build.py
```

成功後輸出為 `dist/MotorControl.exe`。打包版不需要旁邊放置 `analyze.py` 或
`simulate.py`；兩者會包含在 EXE 中，分析圖會寫到所選 CSV 同層的 `analysis/`，
模擬資料則寫到 EXE 同層的 `data/`。建置必須在 Windows 上執行，且執行中的舊版
`MotorControl.exe` 必須先關閉。

## 檔案結構與各自負責什麼

| 檔案 | 負責的事 | 你會改到的地方 |
|---|---|---|
| `config.py` | 所有硬體參數集中 | **每次實驗都要確認** 力臂長度、序列埠 |
| `ak_can.py` | CAN 收發、MIT 協議打包解包 | 幾乎不用改 |
| `loadcell.py` | 序列埠讀 load cell、歸零 | 幾乎不用改 |
| `arduino_loadcell/` | Arduino 端 HX711 讀取 | **校正係數必須實測填入** |
| `logger.py` | 兩路資料同步、寫 CSV、安全檢查 | 加通道時改 `COLUMNS` |
| `experiments.py` | 五組實驗腳本 | 改實驗參數（扭力上限、時長） |
| `analyze.py` | 出圖出數字 | 之後想加新圖表時 |
| `simulate.py` | 產生假資料，無硬體也能跑通全流程 | 不用改 |
| `__main__.py` | 唯一 GUI 入口；建立 `QApplication`、套用樣式並顯示 `MainWindow` | 調整應用程式啟動流程時 |
| `build.py` | 依賴檢查與 PyInstaller 單檔建置 | 調整打包內容時 |
| `src/main_window.py` | `MainWindow` 外殼、選單與關閉時的安全收尾 | 調整主視窗或選單時 |
| `src/application/` | Composer 建立並串接 Panel、Controller 與共用狀態 | 增減主要功能模組時 |
| `src/ui/` | 硬體、實驗、遙測與分析面板 | 調整畫面時 |
| `src/controllers/` | 量測／分析流程協調與安全關閉 | 增加工作流程時 |
| `src/workers/` | 背景硬體量測、模擬與分析程序 | 增加實驗時 |

分層的意義：**量測時一個數字都不要現場算，只記原始值。**
事後發現換算錯了，重跑 `analyze.py` 就好。熱實驗跑一次 15 分鐘，你不會想重做。

## 現在就能做的第一件事（不用任何硬體）

```bash
pip install python-can pyserial pandas matplotlib numpy scipy

python ak_can.py                      # 驗證 MIT 打包邏輯
python simulate.py                    # 產生四組假資料
python analyze.py data/sim_kt_calib.csv
python analyze.py data/sim_thermal_pla.csv
```

假資料裡我故意藏了三個真實現象（Kt 比標稱低 8%、電流 12A 開始飽和、
熱時間常數 240s）。跑一次分析看它有沒有抓出來——抓得出來，代表分析程式沒問題，
硬體到位那天你只要專心處理接線。

## 硬體清單

| 項目 | 說明 | 大約價位 |
|---|---|---|
| CAN 轉接器 | CANable / USB2CAN，Linux 走 socketcan 最省事 | NT$ 500–1500 |
| 120Ω 終端電阻 | **一定要接**，不接會通訊時好時壞，很難查 | NT$ 10 |
| S 型 load cell | 拉壓兩用，量程選 20–50 kgf | NT$ 500–1500 |
| HX711 模組 | 記得改成 80 SPS（見下） | NT$ 50 |
| Arduino Nano / ESP32 | 建議 ESP32，之後加溫度感測器腳位才夠 | NT$ 150–300 |
| 鋁擠型 + 角件 | 基座，一定要鎖死在工作台上 | NT$ 500 |
| 力臂 | 6mm 以上鋁板，沿長度鑽 100/150/200mm 三個孔 | 自製 |
| NTC 熱敏電阻 ×2–4 | 貼定子側與底座，量真實溫度 | NT$ 50 |

**HX711 必須改成 80 SPS。** 模組出廠通常是 10 SPS，對「抬重物」這種秒級動作來說
太慢，會抓不到峰值。做法是把板上 RATE 腳拉到 VCC（有些板子要剪一條短路線）。

## 治具設計的五個關鍵細節

這幾點做不好，你量到的是治具特性不是馬達特性：

1. **力臂要夠剛。** 6mm 鋁板起跳。彎曲會讓有效力臂變短，扭力系統性偏低。
2. **load cell 受力必須垂直於力臂。** 不垂直只量到分力。做法是 load cell 上方
   加一顆鋼珠或半球頂桿，讓接觸點永遠是點接觸、力線通過 load cell 軸心。
3. **量測時力臂保持水平。** 不然要扣力臂自重力矩。最省事的做法就是每次都回到
   水平位置再讀值。
4. **馬達底座要剛。** ⚠️ 你照片裡那顆現在裝在 3D 列印底座上——那個底座**適合當熱
   實驗的 baseline（最差情況），但不適合當扭力量測的基準**。PLA 在 20 N·m 下會
   明顯變形，你會量到「馬達扭力 + 底座回彈」的混合物。扭力校正請換金屬座或加
   強背板。
5. **一定要有機械限位。** AK10-9 V3.0 峰值扭力 53 N·m，力臂 150mm 就是 350 N 的
   端點力。失控時會把桌上的東西掃飛。

## 執行順序（照這個順序做，不要跳）

```bash
# 0. 縮放常數驗證 ★★★ 沒做這步，後面全部數據都不可信
python experiments.py verify
```

這步在驗證兩件事：位置回授的單位、極對數對不對。
原因是 **CubeMars V3.0 手冊自己前後矛盾**：

| 參數 | 手冊 p.38 表格 | 手冊 p.39 範例碼 |
|---|---|---|
| 速度範圍 | ±28.0 rad/s | ±33.0 rad/s |
| 扭力範圍 | ±54.0 N·m | ±65.0 N·m |

用錯 → 你的扭力指令與實際輸出差一個固定比例（54/65 = 0.83），
而且一切看起來都很正常。這就是為什麼 `analyze.py` 會特別報「指令→實測比值」，
如果它接近 0.83 或 1.20，就是這裡填錯了。

```bash
# 1. 扭力常數校正  → 交付物：實測 Kt vs 標稱 Kt、飽和點
python experiments.py kt
python analyze.py data/<最新>_kt_calib.csv

# 2. 正反向不對稱（你問的「抬」vs「頂」）
python experiments.py asym

# 3. 反驅阻力  → 你論文「可反向驅動性」指標的實體基準
python experiments.py backdrive

# 4. 熱衰減  → 甘特圖第 8-12 週的熱特性化
python experiments.py thermal
```

第一次跑請先把 `config.SAFE_TORQUE_MAX` 設成 **3 N·m**，確認治具不會動、
數字合理，再往上調。

## 關於「不同槓桿」這件事

**換力臂長度不會改變馬達能出多少扭力。** τ = Kt × I，跟外面接什麼無關。
所以三組孔位在你的實驗裡有兩個不同用途，別混在一起：

**用途一：量測系統的自我驗證。** 用 100/150/200mm 各量一次同一個電流下的扭力，
三次算出來的 τ 應該一致（差異 <2%）。不一致就是治具有問題——力臂彎曲、
load cell 不垂直、或孔位量錯。**這是必做的健全性檢查，而且是你報告裡
「量測不確定度」那一段的唯一依據。**

**用途二：模擬傳動比。** 你實際上是在畫「給定這顆馬達，不同傳動比下的
端點力—端點速度包絡」。你的踝關節連桿長度就是一個槓桿，所以這條包絡線
直接餵給幾何最佳化。這才是對專題有貢獻的部分。

## 這套東西怎麼接回你的專題

| 產出 | 接到哪裡 |
|---|---|
| 實測 Kt 與標稱的偏差 | 幾何最佳化的扭力模型輸入（不然你是用 datasheet 在算） |
| 飽和點 = 真實可用峰值扭力 | 工作空間分析的扭力上限 |
| 反驅阻力（庫倫 + 黏滯） | 「可反向驅動性」新指標的基準值；SPU/RSU 對照就比這個數字 |
| 熱時間常數 τ、穩態溫升 T∞ | 「熱負載均勻性」成本函數的參數；不同固定座材質的對照 |

四項全部**不需要等機器人做出來、不需要等機構設計凍結**。
這正是你甘特圖裡「熱實驗必須提前」那個前提的具體實作。

而且這台治具跟熱特性化治具是同一台——一份工作兩份產出。

## 常見問題

**收不到 CAN 回授**
依序檢查：120Ω 終端電阻有沒有接、bitrate 是不是 1 Mbps、馬達 ID、
CAN_H/CAN_L 有沒有接反、Linux 有沒有 `sudo ip link set can0 up type can bitrate 1000000`。

**load cell 數字亂跳**
`lc.tare()` 會印出雜訊峰對峰值。超過量程的 0.5% 就是接線問題：
訊號線要屏蔽、遠離馬達動力線、HX711 電源要獨立於馬達電源。

**analyze.py 說剔除比例偏高**
代表兩路資料有一路太慢。HX711 確認在 80 SPS；馬達的 CAN 回授率
在上位機軟體裡調到 200 Hz 以上。

**扭力量到的比指令小很多**
先看 `analyze.py` 報的「指令→實測比值」。接近 0.83 → `config.T_MAX` 應該填 54.0；
接近 1.0 但仍偏低 → 是真實的傳動效率損失，那就是你的研究發現。
